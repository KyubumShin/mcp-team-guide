# 실험 중간 발견: Subagent 위임이 컴팩션을 방지한다

> **날짜**: 2026-03-11
> **실험**: exp_compaction_pass_rate_degradation
> **상태**: 중간 발견 (본 실험 설계 변경 필요)

## 발견

MPL의 orchestrator-worker 패턴에서 **컴팩션이 발생하지 않는다**.

## 데이터

| Run | 태스크 | 실패 테스트 | 결과 | 컨텍스트 사용 | 컴팩션 |
|-----|--------|-----------|------|-------------|--------|
| task2-long-run1 | Scheduler (18 tests) | 18 | 18/18 pass | - | 0회 |
| task5-long-run1 | 전체 통합 (50 tests) | 50 | 81/81 pass | 21% | 0회 |

## 메커니즘

```
오케스트레이터 컨텍스트:
  - 코드 탐색 (Read) → 가벼움
  - Worker 위임 지시 (Agent call) → 가벼움
  - 결과 수신 (요약) → 가벼움
  = 총 ~21% 사용

Worker 컨텍스트 (독립):
  - 각 Worker가 별도 컨텍스트에서 실행
  - 코드 읽기 + 수정 + 테스트 = 무거운 작업
  - 하지만 오케스트레이터에 영향 없음
  - Worker 세션 종료 시 컨텍스트 해제
```

## 결론

**Subagent 위임 자체가 가장 효과적인 컴팩션 내성 메커니즘이다.**

context-engineering/10-compaction-resilience.md에서 정리한 7가지 전략(훅 재주입, 외부 파일, remember 태그 등)보다
근본적인 해결: **무거운 작업을 오케스트레이터 컨텍스트 밖으로 보내는 것**.

이는 컴팩션 "내성"이 아니라 컴팩션 "회피" — 컨텍스트가 쌓이지 않으니 컴팩션이 발생할 이유가 없다.

## 실험 설계 시사점

컴팩션 실험을 하려면:
1. **단일 에이전트** (worker 위임 없이)로 실행해야 컨텍스트가 누적됨
2. 또는 **충분히 큰 프로젝트** (200+ 테스트, 15+ 모듈)에서 오케스트레이터의 탐색/조율 비용이 임계점을 넘도록
3. 실제 프로젝트(Yggdrasil 등)를 대상으로 하면 자연스럽게 컨텍스트 누적 가능
