# Planning Compaction Experiment — 프롬프트 세트

> 각 라운드를 순서대로 입력. 이전 응답을 받은 후 다음 라운드 진행.
> 목적: 오케스트레이터 컨텍스트를 계획 수립으로 누적시켜 컴팩션 유발.

## Round 1: Spec 전체 읽기 + 초기 계획

```
docs/ 디렉토리의 모든 spec 문서를 읽고, Yggdrasil 프로젝트의 전체 구조를 파악해줘.
각 모듈의 역할과 의존관계를 정리하고, 구현 우선순위를 포함한 초기 계획을 만들어줘.
아직 코드 구현은 하지 마 — 계획만 세워줘.
```

## Round 2: Type 정의 분석 + 계획 보완

```
src/types/ 디렉토리의 모든 type 정의 파일을 읽어봐.
이 타입들이 spec과 어떻게 매핑되는지 분석하고,
Round 1의 계획을 type 계약 기반으로 보완해줘.
특히 타입 간 의존관계가 구현 순서에 영향을 미치는 부분을 식별해.
```

## Round 3: 테스트 분석 + 수용 기준 매핑

```
모든 test 파일 (*.test.ts, *.test.tsx)을 읽어봐.
각 테스트가 어떤 기능을 검증하는지 분석하고,
계획의 각 모듈에 대응하는 테스트를 매핑해줘.
테스트에서 요구하지만 spec에 명시되지 않은 암묵적 요구사항도 식별해.
```

## Round 4: 의존관계 그래프 + 구현 순서 재배치

```
지금까지 분석한 내용을 바탕으로:
1. 모듈 간 import 의존관계 그래프를 그려줘
2. 순환 의존성이 있는지 확인해
3. 구현 순서를 dependency-first로 재배치해
4. 각 phase에서 어떤 테스트가 통과 가능해지는지 매핑해
```

## Round 5: 리스크 평가 + 에지케이스 식별

```
각 모듈별로:
1. 구현 난이도를 상/중/하로 평가해
2. 잠재적 에지케이스를 식별해
3. spec과 test 간 불일치가 있는 부분을 찾아줘
4. 가장 실패하기 쉬운 모듈과 그 이유를 설명해
```

## Round 6: 성능 및 상태 관리 분석

```
Zustand store 설계를 깊이 분석해줘:
1. 각 store의 상태 구조와 action을 정리해
2. store 간 cross-reference가 필요한 부분을 식별해
3. 비동기 action의 에러 처리 전략을 계획해
4. 테스트에서 store를 어떻게 mock/reset하는지 분석해
```

## Round 7: 통합 계획 최종 정리

```
지금까지의 모든 분석을 종합해서 최종 구현 계획을 만들어줘:
1. Phase별 구현 대상 모듈과 예상 테스트 통과 수
2. 각 Phase의 전제 조건과 완료 기준
3. Phase 간 의존관계
4. 리스크 완화 전략
5. 예상되는 총 Phase 수와 난이도 분포
```

## Round 8+ (컴팩션 미발생 시 추가 라운드)

```
Round 8: "backend spec의 Tauri command 인터페이스를 상세 분석하고,
          각 command의 입출력 타입과 에러 시나리오를 정리해"

Round 9: "frontend component spec을 분석하고,
          각 컴포넌트의 props/state/event 인터페이스를 정리해"

Round 10: "전체 계획을 비판적으로 검토해.
           빠뜨린 것, 과소평가한 것, 순서가 잘못된 것을 찾아줘"
```

## 관찰 포인트

각 라운드 후 기록:
- [ ] HUD 또는 context_window 사용률 (가능하면)
- [ ] 응답 품질 주관 평가 (1-5)
- [ ] 이전 라운드 내용 참조 정확도
- [ ] 컴팩션 발생 여부 (compactions.jsonl 확인)
