# Phase 2: Incremental - 점진적 구현/테스트 설계

## 목표

Exp 5(테스트 스텁)와 Exp 6(점진적 테스팅)의 핵심 인사이트를 결합하여, **모듈별 구현 → 즉시 테스트 → 실패 시 즉시 수정** 패턴을 MPL 파이프라인의 표준 동작으로 만든다.

## 핵심 원칙

### "Build-Test-Fix" 마이크로 사이클

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   모듈 구현 ──→ 모듈 테스트 ──→ 통과? ──→ 다음 모듈 │
│                                    │                │
│                                    ↓ 실패            │
│                               즉시 수정 ──┘          │
│                                                     │
└─────────────────────────────────────────────────────┘
```

기존 MPL v1.0은 모든 모듈을 구현한 후 Phase 4에서 한꺼번에 테스트했다. 이는 오류가 누적되어 디버깅이 복잡해지는 문제가 있었다. v2.0에서는 각 모듈을 구현한 직후 해당 모듈의 테스트를 실행한다.

## Exp 6 기반 점진적 테스팅 설계

### 테스트 단계 정의

Exp 6에서 검증된 5단계 점진적 테스팅 구조를 표준화한다:

| 단계 | 대상 | 테스트 수 (예시) | 누적 검증 |
|------|------|----------------|----------|
| Stage 1 | 데이터 모델 | 11 | 11 |
| Stage 2 | 핵심 로직 (DAG 등) | 19 | 30 |
| Stage 3 | I/O (로더, 파서) | 15 | 45 |
| Stage 4 | 실행/오케스트레이션 | 14 | 59 |
| Stage 5 | 통합 + 히든 테스트 | 18 | 77 |

### 실험 근거

Exp 6 결과:
- Phase 1 (Models): 11/11 (100%) - 0.01s
- Phase 2 (DAG): 19/19 (100%) - 0.02s
- Phase 3 (Loader): 15/15 (100%) - 0.01s
- Phase 4 (Executor): 14/14 (100%) - 2.05s
- Phase 5 (Full): 77/77 (100%) - 2.10s

**핵심 발견**: 모든 단계에서 0개의 수정이 필요했다. 이는 Phase 0 강화(Exp 1~4, 7)와 점진적 테스팅의 시너지를 보여준다.

## Exp 5 기반 스텁 우선 개발 통합

### TDD 플로우

Exp 5의 테스트 스텁 생성 접근법을 Phase 0 산출물과 결합한다:

```
Phase 0 산출물          스텁 생성              전체 구현
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ API 계약     │───→│ 최소 스텁    │───→│ 완전한 구현   │
│ 예제 패턴    │    │ (인터페이스) │    │ (로직 채움)   │
│ 타입 정책    │    │              │    │              │
│ 에러 명세    │    │ 샘플 테스트  │    │ 전체 테스트   │
│              │    │ 통과 확인    │    │ 통과 확인    │
└──────────────┘    └──────────────┘    └──────────────┘
```

### 스텁 검증 체크리스트

각 모듈 스텁이 충족해야 할 조건:

- [ ] 모든 공개 함수/클래스가 정의됨
- [ ] 시그니처가 API 계약과 일치
- [ ] 타입 힌트가 타입 정책을 따름
- [ ] 기본값이 예제 패턴과 일치
- [ ] 에러 조건이 에러 명세를 따름
- [ ] 해당 모듈의 샘플 테스트 통과

## Phase Runner 변경사항

### Incremental Verification 모드 추가

기존 Phase Runner에 `incremental` 모드를 추가한다:

```python
# 기존 모드
mode: "batch"  # 모든 모듈 구현 후 한번에 테스트

# 신규 모드
mode: "incremental"  # 모듈별 구현-테스트 사이클
```

### 동작 방식

```
Phase 1 (Models) 구현
  → pytest tests/test_models.py 실행
  → 실패 시: 즉시 수정 후 재테스트
  → 통과 시: Phase 2로 진행

Phase 2 (Core Logic) 구현
  → pytest tests/test_models.py tests/test_core.py 실행
  → 이전 단계 테스트도 포함 (회귀 방지)
  → 실패 시: 즉시 수정
  → 통과 시: Phase 3으로 진행

Phase 3 (I/O) 구현
  → pytest tests/ 전체 실행
  → 실패 시: 즉시 수정
  → 통과 시: 통합 테스트 진행
```

### 실패 처리 정책

| 실패 유형 | 처리 방식 | 최대 재시도 |
|----------|----------|-----------|
| 현재 모듈 테스트 실패 | 즉시 수정 후 재테스트 | 3회 |
| 이전 모듈 회귀 | 회귀 원인 분석 후 수정 | 2회 |
| 타입 에러 | Phase 0 타입 정책 재확인 | 2회 |
| 에러 메시지 불일치 | Phase 0 에러 명세 재확인 | 2회 |

## Phase 5 진입 조건 엄격화

### 현재 (v1.0)

```
Phase 4 완료 → 무조건 Phase 5 진입 (수정 사이클)
```

### 변경 (v2.0)

```
Phase 4 완료
  → 통과율 >= 95%? → 완료 (Phase 5 스킵)
  → 통과율 < 95%?  → Phase 5 진입 (최소 수정만)
```

### 세부 조건

| 통과율 | 동작 |
|--------|------|
| 100% | 즉시 완료 |
| 95~99% | 실패 테스트만 분석, 최소 수정 후 완료 |
| 80~94% | Phase 5 경량 수정 (1회 사이클) |
| <80% | Phase 0 재검토 필요 (비정상 상태) |

## 복잡도 자동 감지기 설계

### 입력

```python
def detect_complexity(project_path: str) -> ComplexityLevel:
    """프로젝트를 분석하여 복잡도 등급을 반환한다."""
```

### 분석 항목

| 항목 | 가중치 | 측정 방법 |
|------|--------|----------|
| 모듈 수 | x10 | 디렉토리 내 .py 파일 수 |
| 외부 의존성 | x5 | requirements.txt / import 분석 |
| 테스트 수 | x2 | test_*.py 파일의 테스트 함수 수 |
| 비동기 함수 | x8 | async def 카운팅 |
| 클래스 수 | x3 | class 정의 수 |
| 순환 의존성 가능성 | x15 | 상호 import 분석 |

### 출력

```python
@dataclass
class ComplexityResult:
    level: str          # "simple" | "medium" | "complex" | "enterprise"
    score: int          # 0~300+
    breakdown: dict     # 항목별 점수
    recommended_steps: list  # Phase 0에서 실행할 Step 목록
    token_budget: int   # 예상 토큰 예산
```

## 예상 효과

### 정량적 효과

| 지표 | v1.0 | v2.0 (Incremental) | 개선 |
|------|------|-------------------|------|
| 디버깅 사이클 | 3~5회 | 0~1회 | -80% |
| Phase 5 진입률 | 100% | <5% | -95% |
| 오류 발견 시점 | Phase 4 (늦음) | 구현 직후 (빠름) | 조기 발견 |
| 컨텍스트 전환 비용 | 높음 | 낮음 | 집중도 유지 |

### 정성적 효과

1. **빠른 피드백**: 구현 직후 테스트 결과를 확인하여 기억이 신선할 때 수정
2. **회귀 방지**: 누적 테스트로 이전 모듈의 정상 동작을 지속 보장
3. **신뢰 구축**: 단계별 통과가 개발자/에이전트의 자신감을 점진적으로 높임
4. **디버깅 용이**: 실패 시 원인을 현재 모듈로 즉시 좁힐 수 있음
